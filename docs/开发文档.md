## 一、项目概述

### 1.1 项目背景

基于微信公众号平台，构建一套智能客服系统。用户通过微信公众号发送文本、图片、语音消息，系统接入大语言模型（LLM）进行智能回复，支持文本、图片、语音三种回复形式。

### 1.2 核心目标

| 目标 | 说明 |
|------|------|
| 微信接入 | 对接微信公众号开发接口，完成服务器验证与消息收发 |
| 消息收发 | 支持接收/发送文本、图片、语音消息 |
| LLM 智能回复 | 接入大模型 API，实现文本生成、图片生成/理解、语音合成 |
| 实时天气 | 地点解析为经纬度后查询当前天气与未来 7 天预报 |
| 地点搜索 | 使用高德 POI 数据查询指定城市的景点、餐厅、医院等地点 |
| 可扩展架构 | 模块化设计，支持后续扩展更多消息类型和模型能力 |

### 1.3 技术选型

| 层级 | 技术 | 说明 |
|------|------|------|
| 语言 | Java 17 | LTS 版本，稳定可靠 |
| 构建工具 | Maven 3.9+ | 标准化依赖管理 |
| Web 框架 | Spring Boot 3.2 | 快速构建 RESTful 服务 |
| 微信 SDK | WxJava (`weixin-java-mp`) | 成熟的微信公众号 Java SDK |
| LLM 接入 | OpenAI兼容接口 / 通义千问 | 支持 text/image/voice 多模态 |
| 地理数据 | 高德 Web 服务 + Open-Meteo | 高德提供国内天气和 POI；天气失败时可降级 |
| HTTP 客户端 | OkHttp | 调用 LLM API |
| JSON 处理 | Jackson | 消息序列化/反序列化 |
| 日志 | Logback | Spring Boot 内置 |
| 部署 | Docker + Nginx | 容器化部署，Nginx 反向代理 |

## 三、详细设计

### 3.1 微信公众号接入

#### 3.1.1 公众号配置

| 配置项 | 说明 |
|--------|------|
| AppID | 公众号唯一标识 |
| AppSecret | 公众号密钥 |
| Token | 服务器验证 Token（自定义） |
| EncodingAESKey | 消息加解密密钥 |
| 服务器URL | `https://域名/wx/msg` |

#### 3.1.2 服务器验证

微信服务器会向配置的 URL 发送 GET 请求，携带 `signature`、`timestamp`、`nonce`、`echostr` 参数。服务端需验证签名后原样返回 `echostr`。

> 使用 WxJava SDK 自动完成签名验证，无需手动实现。

#### 3.1.3 消息接收

微信将用户消息以 XML 格式 POST 到服务器 URL，支持的消息类型：

| 消息类型 | XML MsgType | 关键字段 |
|----------|-------------|----------|
| 文本 | `text` | `Content` - 文本内容 |
| 图片 | `image` | `PicUrl` - 图片URL |
| 语音 | `voice` | `MediaId` / `Recognition`（需开启语音识别） |
| 事件 | `event` | `Event` - 事件类型 (subscribe/CLICK等) |

#### 3.1.4 消息发送

通过微信接口主动发送消息或被动回复消息：

- **被动回复**: 收到用户消息后，在 5 秒内返回 XML 格式的回复消息
- **客服消息**: 通过客服接口主动推送（用于异步场景，如 LLM 响应较慢时）

**被动回复消息格式**:

```xml
<!-- 文本 -->
<xml>
  <ToUserName><![CDATA[用户openid]]></ToUserName>
  <FromUserName><![CDATA[公众号原始ID]]></FromUserName>
  <CreateTime>时间戳</CreateTime>
  <MsgType><![CDATA[text]]></MsgType>
  <Content><![CDATA[回复内容]]></Content>
</xml>

<!-- 图片 -->
<xml>
  <ToUserName><![CDATA[用户openid]]></ToUserName>
  <FromUserName><![CDATA[公众号原始ID]]></FromUserName>
  <CreateTime>时间戳</CreateTime>
  <MsgType><![CDATA[image]]></MsgType>
  <Image>
    <MediaId><![CDATA[素材ID]]></MediaId>
  </Image>
</xml>

<!-- 语音 -->
<xml>
  <ToUserName><![CDATA[用户openid]]></ToUserName>
  <FromUserName><![CDATA[公众号原始ID]]></FromUserName>
  <CreateTime>时间戳</CreateTime>
  <MsgType><![CDATA[voice]]></MsgType>
  <Voice>
    <MediaId><![CDATA[素材ID]]></MediaId>
  </Voice>
</xml>
```

### 3.2 LLM 大模型接入

#### 3.2.1 模型选型

| 能力 | 推荐模型 | 备选 | 说明 |
|------|----------|------|------|
| 意图识别 | 通义千问 `qwen-flash` | 本地规则 | 输出结构化意图与参数 |
| 文本对话 | 通义千问 `qwen-plus` | GPT-4o / DeepSeek | 支持多轮对话 |
| 图片理解 | 通义千问 `qwen-vl-plus` | GPT-4o | 理解用户发送的图片 |
| 图片生成 | 通义万相 `wanx-v1` | DALL-E 3 | 根据文本生成图片 |
| 语音识别 | 通义千问 `qwen3-asr-flash` | Fun-ASR | 将微信语音转成文字 |
| 语音合成 | `cosyvoice-v3-flash` | Azure TTS | 文本转 MP3 语音 |

> 优先使用阿里云通义系列模型（国内访问稳定、API 兼容性好），通过 DashScope API 调用。

#### 3.2.2 API Key 管理

```yaml

  provider: dashscope  # 大模型服务商
  dashscope:
    api-key: ${DASHSCOPE_API_KEY}  # 从环境变量读取，不硬编码
    base-url: https://dashscope.aliyuncs.com/api/v1
    intent-model: qwen-flash
    text-model: qwen-plus
    vision-model: qwen-vl-plus
    image-model: wanx-v1
    asr-model: qwen3-asr-flash
    tts-model: cosyvoice-v3-flash
    tts-voice: longanyang
    tts-format: mp3
    tts-sample-rate: 22050
```

#### 3.2.4 意图识别设计

文本消息先经过混合意图分类器：明确命令由本地规则处理，其他表达由 `qwen-flash` 结合最近 6 条对话分类。语音消息完成转写后也进入同一套分类和路由。模型使用 JSON Mode 返回 `intent`、`confidence`、`slots`、`replyMode`、`needsClarification` 和 `clarificationQuestion`。

普通聊天使用匿名、克制、务实的性格规则，不包含现实人物姓名或身份信息。输出默认采用自然微信聊天文本，禁止客服套话、角色标签和未填充模板字段；`ChatReplyFormatter` 对常见角色前缀与占位符做最后清理，但保留代码块和必要的结构化步骤。

允许的意图仅包括：

- `CHAT`：普通聊天与问答
- `WEATHER`：查询实时天气或未来预报，必须提供 `slots.location`，日期放入 `slots.date`
- `PLACE_SEARCH`：搜索现实地点，必须提供 `slots.location` 和 `slots.keyword`
- `GENERATE_IMAGE`：生成图片，必须提供 `slots.prompt`
- `CLEAR_CONTEXT`：清除当前用户对话历史
- `HELP`：返回功能说明
- `UNKNOWN`：信息不足，需要追问

所有模型结果必须经过枚举白名单、必填参数和置信度校验。动作意图置信度低于 `0.75` 时不执行；模型调用或 JSON 解析失败时降级为普通聊天。

天气意图不会让 LLM 直接生成天气内容。配置高德 Web 服务 Key 后，`WeatherService` 先把详细地址解析为行政区 `adcode`，再查询实况和预报；未配置 Key 或高德请求失败时，降级为 Open-Meteo 的经纬度天气。支持 `TODAY`、`TOMORROW`、`DAY_AFTER_TOMORROW`、`NEXT_3_DAYS`、`NEXT_7_DAYS` 和具体日期，回复中回显解析后的地点和数据更新时间。

天气与地点搜索均实现 `AiTool`，由 `ToolRegistry` 按名称执行。`WeatherTool` 包装 `WeatherService`；`PlaceSearchTool` 调用高德 `/v3/place/text`，限定城市并返回前 5 个 POI。工具输出直接进入聊天上下文和微信回复，不再交给 LLM 改写事实数据。

`replyMode` 不是新的业务意图，而是与意图正交的回复方式：`AUTO` 表示使用默认值，`TEXT` 表示文字回复，`VOICE` 表示语音回复。文字和语音输入都默认 `TEXT`，只有用户明确要求语音回答时才使用 `VOICE`。语音合成或发送失败时自动降级为文字；图片生成意图仍发送图片。

### 3.3 消息处理器设计

采用策略模式，按消息类型分发到不同 Handler：

```
MessageHandler (接口)
├── boolean supports(String msgType)
└── WxMpXmlOutMessage handle(WxMpXmlMessage inMessage)

TextMessageHandler     # 文本消息 → 异步意图识别 → 功能路由
ImageMessageHandler    # 图片消息 → LLM图片理解
VoiceMessageHandler    # 语音消息 → 程序内ASR → 共用意图路由（默认文字回复）
EventMessageHandler    # 事件消息 (关注/菜单点击等)
```

### 3.4 异步处理机制

由于 LLM 响应可能超过微信 5 秒限制，采用异步策略：

```
用户消息到达
    │
    ├─ 立即回复 "正在思考中..." (被动回复，满足5秒限制)
    │
    └─ 异步线程处理:
         ├─ 调用 LLM 获取回复
         ├─ 如果回复是图片 → 上传微信素材 → 获取 MediaId
         ├─ 如果回复是语音 → 上传微信素材 → 获取 MediaId
         └─ 通过客服消息接口主动推送最终回复
```

### 3.5 微信素材管理

发送图片和语音消息需要先上传素材获取 `MediaId`：

```
上传流程:
1. LLM 生成图片/语音 → 获取文件
2. 调用微信素材上传接口 (POST /media/upload)
3. 获取 media_id
4. 使用 media_id 构建回复消息
```

### 3.6 自主规划能力层（连接 Agent、Tool 与 Skill）

用户只给出一个高层目标（如“制定上海三日游方案”）时，系统需要先拆解子任务、再根据执行结果决定下一步，最终输出完整成品。为此在“意图识别 + 工具调用”之上增加一层**统一能力层**：`Agent/Planner` 通过 `CapabilityRegistry` 发现并执行 `Tool`（原子能力）或 `Skill`（复合业务能力）。本节只规定各模块的职责边界与对接方式；Agent 循环、Planner/Replanner 与具体 Skill 尚未实现，属于后续任务。

#### 3.6.1 模块职责与业务边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| **Agent / Planner**（后续实现） | 接收高层目标；拆解至少 3 个子任务；决定每一步调用哪个能力；维护状态、最大步数与结束条件；根据 `CapabilityResult` 决定继续或结束 | 不直接 `new` Tool/Skill；不直接调 `ToolRegistry`/`SkillRegistry`；不实现具体业务能力（查天气、生成路线等） |
| **CapabilityRegistry**（已完成） | 统一列出可用能力（`listCapabilities`）；统一执行入口（`execute`）；按名字路由到 Tool 或 Skill；检测 Tool 与 Skill 同名冲突；把结果统一归一为 `CapabilityResult` | 不实现任何业务；不做意图识别；不做任务拆解与循环控制；不调用 LLM |
| **Tool**（`AiTool` 实现） | 实现单个确定性原子能力（天气、地点搜索、联网搜索、计算等）；校验自身参数；返回格式化文本 | 不做多工具编排；不决定何时被调用；不管理多轮对话状态 |
| **Skill**（`Skill` 实现） | 封装一个完整业务能力；内部编排多个 Tool 与 LLM（后续可加 RAG）；输出完整成品 | 不替代 Tool 做原子能力；不做意图识别；不做 Agent 循环 |

#### 3.6.2 调用链

```
用户目标（如“上海三日游完整方案”）
  → 消息通道 → TextProcessingService → IntentClassifier（识别为“自主规划”类意图）
  → Agent Loop（后续：#1，维护状态 / 最大步数 / 结束条件）
      → Planner（后续：#2）读 CapabilityRegistry.listCapabilities() 选出能力
      → CapabilityRegistry.execute(name, userId, args)      ← 已完成
            ├─ 命中 Tool  → ToolRegistry.execute → AiTool.execute → String → CapabilityResult
            └─ 命中 Skill → SkillRegistry.execute → Skill.execute
                              └─ Skill 内部通过注入的 ToolRegistry 调 Tool、通过 LlmService 调 LLM
                          → SkillResult → CapabilityResult
      → Agent 依据 CapabilityResult 决定下一步 / 结束
  → 最终成品经 WxMessageService 发出
```

#### 3.6.3 为什么需要 CapabilityRegistry

改造前，若 Agent 直接依赖各类 Tool/Skill，会带来四个问题：一是返回类型不统一（`AiTool.execute` 返回 `String`，`Skill.execute` 返回 `SkillResult`），Agent 需要分别处理；二是没有统一的能力清单，Agent 无法一次性知道“有哪些能力、各自要什么参数”；三是 Tool 与 Skill 可能同名，Agent 无法判断该调用谁；四是每新增一个能力都要改动 Agent 的调用代码。

`CapabilityRegistry` 把“发现”和“执行”收口到一处：`listCapabilities()` 提供统一的 `name/description/inputSchema/kind` 元数据，`execute()` 对上层只返回一种 `CapabilityResult`，同名冲突在启动时即报错，新增 Tool 或 Skill 无需改动 Agent。

#### 3.6.4 新增代码落点（在哪个类里写）

| 要做的事 | 落点 |
| --- | --- |
| 新增一个原子工具 | `com.group4.wxai.service.tool` 包，新建 `@Component` 类实现 `AiTool`，`name()` 用唯一英文名，重写 `execute(Map)` 返回格式化文本 |
| 新增一个业务 Skill | `com.group4.wxai.service.skill` 包，新建 `@Component` 类实现 `Skill`，`name()` 用唯一英文名，实现 `execute(SkillContext, Map)` |
| Skill 调用 Tool | 注入 `ToolRegistry`，按名调用 `toolRegistry.execute("weather", Map.of(...))`，禁止直接 `new` 具体工具 |
| Agent 执行 Tool / Skill | 只调用 `CapabilityRegistry.execute(name, userId, args)`；发现能力用 `CapabilityRegistry.listCapabilities()` |
| Planner / Replanner | 后续放在 `com.group4.wxai.service.agent`，负责拆解子任务、依据 `CapabilityResult` 决定下一步 |
| Agent Loop | 后续放在 `com.group4.wxai.service.agent`，负责状态、最大步数、结束条件，并驱动 Planner 与 `CapabilityRegistry` |
| 不要写进 `CapabilityRegistry` | 业务逻辑、意图识别、LLM 调用、任务拆解、循环控制、RAG 检索 |
| 不要写进具体 Tool / Skill | 意图识别、任务拆解、Agent 状态、直接发送微信消息（应返回结果交由上层发送） |

#### 3.6.5 后续模块对接边界

- **Planner / Replanner**：只依赖 `CapabilityRegistry.listCapabilities()` 与 `execute()`，通过返回的 `CapabilityResult` 的 `ok/output/errorMessage` 决定下一步。
- **Agent Loop**：维护用户级状态与步数，每一步调用 `CapabilityRegistry.execute()` 并把返回的 `CapabilityResult` 作为 observation；到达最大步数或目标达成时结束。
- **旅游路线规划 Skill / 当天行程规划 Skill**：实现 `service.skill.Skill`，注入 `ToolRegistry`（调 `weather`/`place_search`/`web_search`）与 `LlmService`（成稿），在 `execute` 内编排并返回 `SkillResult`。
- **RAG**：作为独立服务（如 `service.rag`）由 Skill 内部注入调用，是 Skill 的数据来源，不作为 `CapabilityRegistry` 管理的能力。

## 六、接口清单

### 6.1 微信消息接口

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 服务器验证 | GET | `/wx/msg` | 微信服务器签名验证 |
| 消息接收 | POST | `/wx/msg` | 接收用户消息并回复 |

### 6.2 LLM 服务接口 (内部调用)

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| `chatText` | 用户文本 + 历史对话 | 回复文本 | 文本对话 |
| `chatWithImage` | 用户文本 + 图片URL | 回复文本 | 图片理解 |
| `generateImage` | 提示词 | 图片URL | 图片生成 |
| `textToSpeech` | 文本 | 音频数据 + 格式 | 语音合成 |

### 6.3 微信素材接口 (内部调用)

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| `uploadImage` | 图片文件 | mediaId | 上传图片素材 |
| `uploadVoice` | 语音文件 | mediaId | 上传语音素材 |
| `sendCustomMessage` | openid + 消息体 | void | 发送客服消息 |

### 6.4 AI 工具接口（内部调用）

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| `ToolRegistry.execute("weather", ...)` | `location` + `date` | 格式化天气文本 | 调用 `WeatherTool` 查询实时天气及最多 7 天预报 |
| `ToolRegistry.execute("place_search", ...)` | `location` + `keyword` | POI 列表文本 | 调用 `PlaceSearchTool` 返回指定城市前 5 个地点 |

### 6.5 Agent 能力层接口（内部调用）

Agent/Planner 通过以下接口发现并执行 Tool 与 Skill。执行入口统一为 `CapabilityRegistry`，不要直接依赖 `ToolRegistry` 或 `SkillRegistry`。

**AiTool**（`service/tool/AiTool.java`）—— 原子工具契约

| 方法 | 说明 |
| --- | --- |
| `String name()` | 工具唯一名，如 `weather` |
| `String description()` | 工具用途说明 |
| `String inputJsonSchema()` | 输入参数 JSON Schema，默认空对象 |
| `String execute(Map<String,String> arguments)` | 执行并返回格式化文本 |
| `String execute(ToolExecutionContext context, Map<String,String> arguments)` | 带用户上下文的默认重载，默认委托给上一方法 |

**ToolRegistry**（`service/tool/ToolRegistry.java`）—— 工具注册与执行

| 方法 | 说明 |
| --- | --- |
| `ToolRegistry(List<AiTool> toolList)` | Spring 注入全部 `AiTool`，按 `name()` 注册，重名抛 `IllegalStateException` |
| `String execute(String toolName, Map<String,String> args)` | 按名执行 |
| `String execute(String toolName, String userId, Map<String,String> args)` | 带用户上下文执行 |
| `Set<String> names()` | 已注册工具名 |
| `Map<String, AiTool> all()` | 只读工具映射，供 `CapabilityRegistry` 读取元数据 |

**Skill**（`service/skill/Skill.java`）—— 复合能力契约

| 方法 | 说明 |
| --- | --- |
| `String name()` | 技能唯一名，如 `travel_route` |
| `String description()` | 技能用途说明 |
| `String inputJsonSchema()` | 输入参数 JSON Schema，默认空对象 |
| `SkillResult execute(SkillContext context, Map<String,String> arguments)` | 执行并返回结构化结果 |

**SkillContext**（`service/skill/SkillContext.java`）—— `record SkillContext(String userId)`，空值归一为 `anonymous`，提供 `anonymous()`。

**SkillResult**（`service/skill/SkillResult.java`）—— `record SkillResult(boolean ok, String output, String errorMessage)`，提供 `success(String)` 与 `failure(String)`。

**SkillRegistry**（`service/skill/SkillRegistry.java`）—— 技能注册与执行

| 方法 | 说明 |
| --- | --- |
| `SkillRegistry(List<Skill> skillList)` | 按 `name()` 注册，重名抛 `IllegalStateException` |
| `SkillResult execute(String skillName, Map<String,String> args)` | 按名执行 |
| `SkillResult execute(String skillName, String userId, Map<String,String> args)` | 带用户上下文执行 |
| `Set<String> names()` | 已注册技能名 |
| `Map<String, Skill> all()` | 只读技能映射 |

**CapabilityKind**（`service/capability/CapabilityKind.java`）—— 枚举 `TOOL` / `SKILL`。

**CapabilitySpec**（`service/capability/CapabilitySpec.java`）—— `record CapabilitySpec(String name, String description, String inputJsonSchema, CapabilityKind kind)`，能力元数据。

**CapabilityResult**（`service/capability/CapabilityResult.java`）—— `record CapabilityResult(boolean ok, String output, String errorMessage)`，提供 `success(String)` 与 `failure(String)`。

**CapabilityRegistry**（`service/capability/CapabilityRegistry.java`）—— 统一能力门面

| 方法 | 说明 |
| --- | --- |
| `CapabilityRegistry(ToolRegistry toolRegistry, SkillRegistry skillRegistry)` | 注入两个注册中心，构造时检测 Tool 与 Skill 同名冲突 |
| `List<CapabilitySpec> listCapabilities()` | 返回全部 Tool 与 Skill 的元数据 |
| `CapabilityResult execute(String capabilityName, Map<String,String> args)` | 统一执行 |
| `CapabilityResult execute(String capabilityName, String userId, Map<String,String> args)` | 带用户上下文统一执行，未找到能力抛 `IllegalArgumentException` |

## 九、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| LLM 响应超时 (>5s) | 微信重试推送 | 异步处理 + 客服消息推送 |
| 微信素材上传失败 | 图片/语音无法回复 | 重试机制 + 降级为文本回复 |
| API Key 泄露 | 安全风险 | 环境变量管理，不提交代码 |
| 公众号接口权限不足 | 部分功能不可用 | 确认公众号已认证，获取所需接口权限 |
| 微信语音识别未开启 | 程序内 ASR 失败时没有微信转写兜底 | 公众号后台开启“语音识别”功能 |
| 天气接口不可用或地点有歧义 | 无法得到可靠天气 | 回显解析地点；失败时提示补充地区或稍后重试 |

### B. DashScope API Key 申请流程

1. 注册阿里云账号并实名认证
2. 开通 DashScope 服务: https://dashscope.console.aliyun.com/
3. 进入 API-KEY 管理，创建新的 API Key
4. 将 API Key 配置到环境变量 `DASHSCOPE_API_KEY`

### C. 微信公众号配置流程

1. 注册微信公众号 (订阅号/服务号)
2. 进入"开发 → 基本配置"，获取 AppID 和 AppSecret
3. 配置服务器地址、Token、EncodingAESKey
4. 开启"语音识别"功能 (开发 → 接口权限)
5. 确保服务器已部署并可外网访问

### D. 高德天气 Key 配置流程

1. 注册高德开放平台开发者账号
2. 创建应用，并添加“Web 服务 API”类型的 Key
3. 将 Key 写入 `.env` 的 `AMAP_WEATHER_API_KEY`
4. 重启 Spring Boot 应用使配置生效
